The core problem, up front

Why two independent UDN subnets can't route to each other on a symmetric-IRB EVPN fabric

Standard EVPN fabrics route between subnets inside one VRF via a single L3VNI (symmetric IRB). OVN-Kubernetes gives every UDN its own macVRF — and, if present, its own unique ipVRF / L3VNI. Three failure modes follow directly from that mismatch:

1. Different L3VNI, different VRF. Symmetric IRB routes by L3VNI — two unique VNIs can never share a VRF, so A and B stay unreachable even with EVPN fully up.

2. macVRF-only is a dead end, not just L2. Primary UDN keeps OVN as GW and keeps IPAM mandatory — there is no way to disable it and hand the subnet to the fabric.

3. No many-VLANs-to-few-VRFs join. Real fabrics group ~100s of VLANs into ~10 VRFs. CUDN only offers a strict 1-UDN-to-1-VRF join — it cannot drop into an existing grouped VRF.

Three symptoms, one root cause: OVN's per-UDN L3 identity model does not match how real fabrics group subnets into VRFs. Everything else in this talk is us discovering that the hard way.
This is the one slide to anchor the whole talk — if people remember one picture, make it this one. Walk left to right: (1) different L3VNI ⇒ different VRF ⇒ no intervlan even with symmetric IRB fully configured; (2) macVRF-only is not a lesser version of L3 — it is zero L3, because OVN keeps the gateway and mandatory IPAM; (3) real fabrics are many-VLANs-to-few-VRFs, CUDN today is strictly 1:1, so there's no way to land an existing fabric VRF group. Resist going deep on BGP/VXLAN mechanics here — that's the chronology section next. Everything downstream (L2 trap, the wall, three locked doors) is a concrete instance of one of these three pictures.

The thesis

We thought OpenShift nodes were just another EVPN leaf

We were joining a standard leaf–spine fabric. We ended up inventing a parallel L3 model.

What we assumed

Peer EVPN. Stretch VLANs. Use fabric anycast for intervlan. Map many CUDNs into ~10 fabric VRFs like every other leaf.

What CUDN actually is today

Great L2 VTEP. Optional per-CUDN ipVRF. OVN owns .1. 1:1 macVRF↔ipVRF. Unique L3 VNIs. Not a standard many-VLAN leaf.

This is narrative A. Park the lab ASN numbers unless asked. Emphasize ‘standard fabric’ = many VLANs / few VRFs / symmetric IRB — not our 3-CUDN toy topology.

Getting on the fabric

Act 1 — Control plane

eBGP multihop from nodes to fabric leaf loopbacks

What worked

Outbound eBGP EVPN. sourceaddress: lo. Multihop. RouteAdvertisements with the right CUDN labels. Type-2/Type-5 once labels matched.

What we learned

Per-interface peering is horrible — peer loopbacks. FRR-k8s does not accept inbound :179. Label mismatch = silent “no networks selected”.

Peering is solvable. It is not the product gap.
Ops learning from Learnings.md: lo↔lo + statics + multihop. Mention FRR inbound only as a P3 ergonomics RFE later — do not derail.
~2 min

Underlay bites

Act 1 — Data plane prerequisite

ARP and BGP looked fine. VXLAN was blackholed.

Control plane path ≠ VXLAN underlay path. VTEP CIDRs must be bidirectionally reachable on the interfaces that carry UDP/4789.

We spent real time here. Fixing underlay feels like victory — and it is necessary — but it does not unlock multi-VLAN leaf behaviour.

Good place for a war story if the room wants one: ARP OK, ping fail, statics on wrong NIC, API path conflict later. Then move on — underlay is table stakes.
~4 min

Same-subnet L2 — the false summit

Act 2 — L2 stretch

Technically works. Useless as a leaf mode.

What we saw

Pod ↔ VM ↔ external host on the same /24. Type-2 MACs. Cross-cluster L2 after underlay fixed. Blue-320 / green-319 stretch.

Why it is not integration

OVN owns .1 + mandatory IPAM. Fabric anycast GW unreachable. OVN GW has no external routes. Pods cannot leave the subnet.

Do not celebrate “L2 works” as fabric success — the leaf is stranded on its /24.
This is the split-chat correction. Pause for discussion. Ask: would you ship this to a customer who expects intervlan via fabric CRB? Answer should be no.

Act 3 — Narrow L3 win

Matching ipVRF to fabric L3VNI + RT — once

This proves EVPN L3 can work. It also sets the trap: “just do that for every VLAN.”

Door 1 — Use the fabric SVI

1

Classic CRB: L2 stretch + fabric anycast for L3

  • Locked by: OVN owns Primary .1 and answers ARP (0a:58:…)
  • Also: defaultGatewayIPs does not hand off ownership; IPAM is mandatory on Primary
  • Also: OVN GW has no external routes — even on-box, pods cannot leave the /24 without ipVRF
    • Fabric SVIs already work for external hosts. Pods never reach them. → RFE-3

    Door 2 — One fabric VRF per CUDN + leak

    2

    Hub-and-spoke: Vrf_BLUE / Vrf_GREEN → leak into CORE

  • Locked by: Target is ~10 VRFs, not ~100s — one CUDN per VRF invents a parallel fabric
  • Also: One fabric VRF ↔ one L3VNI; leak-NH patterns do not scale as a product answer
  • Also: Still needs packets to leave the node (door 1) or shared OVN L3 (door 3)

    Door 3 — Share RT into the fabric VRF

    3

    Unique OVN L3 VNIs + import fabric RT (or multi-RT into CORE)

  • Locked by: Symmetric IRB demuxes on L3VNI, not RT alone
  • Also: OVN rejects two CUDNs on the same fabric L3VNI

    Why CUDNs never route to each other on a standard fabric

    No fabric GW

    Door 1 — OVN owns .1

    No ~100 VRFs

    What we learned

    • Ops: Peer lo↔lo + multihop; fix underlay before debugging overlay; RA labels matter.
    • Product: L2 stretch ≠ leaf integration when OVN owns GW and has no external routes.
    • Product: One CUDN ↔ one fabric VRF is a lab pattern, not a scale pattern.
    • Product: Shared RT is not shared L3VNI under symmetric IRB — so inter-CUDN cannot round-trip via fabric gateways.
    • Architecture: Preferred: shared L3VNI membership → fabric owns intervlan. “Fix it with leak” recreates ~100 VRFs; both fail the standard bar.
    • Process: Write down false summits (L2 works, defaultGatewayIPs) so the next engineer does not re-celebrate them.
    Invite peers to add learnings. Capture on a sticky if useful. Point to catalog + Learnings.md as living docs.
    ~3 min

    What we would tell a customer tomorrow

    Yes: Stretch a VLAN with EVPN CUDN. Peer as a VTEP. Put one Primary network into one fabric VRF with matching L3VNI/RT.

    No / not yet: Drop OpenShift into an existing fabric as a peer leaf for hundreds of VLANs across ~10 VRFs with fabric anycast intervlan — without product gaps closing.

    Do not: Promise that defaultGatewayIPs hands L3 to the fabric, or that sharing a route-target alone joins CORE.

    Honesty builds trust — the narrow wins are real; the scale story needs RFEs.
    Role-play a customer ask if time. Soft-sell the five RFEs; do not read all acceptance criteria — point to the product deck.
