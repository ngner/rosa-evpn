The topic

Can CUDN EVPN integrate OpenShift as an extra leaf on a standard fabric?

Question: can Primary CUDN + ipVRF + FRR-k8s + RouteAdvertisements behave like a normal EVPN leaf — peering into an existing leaf–spine fabric with symmetric IRB?

What “standard fabric” means

Almost every leaf–spine EVPN design is ~100s of VLANs into several VRFs (typically on the order of ~10), plus external VTEPs already on those VRFs. That scale is the bar — not a lab of two or three segments.

Why that bar matters

If CUDN only works for one VLAN per VRF, OpenShift is not a peer leaf on a real fabric. The product must target ~100s of VLANs and several VRFs, or customers cannot integrate without redesigning the fabric around OVN.

What worked

The only off-subnet path today — and what it forces on the fabric

Same-subnet L2 — not a win

Type-2 on-subnet works. Pods still cannot leave: OVN owns .1, fabric GW unreachable, OVN GW has no external routes, Primary IPAM cannot be removed.

What actually worked (narrow)

One VLAN ↔ one CUDN ↔ one ipVRF with L3VNI/RT matching a fabric VRF (e.g. VNI 10000). That single CUDN gets Type-5 off-subnet into that VRF.

How you would have to scale that without shared L3VNI membership: each extra VLAN needs its own CUDN ipVRF (unique L3VNI) → a matching VRF on the fabric leaves → then VRF route-leak into a shared core VRF. For ~100s of VLANs that is ~100s of fabric VRFs + leak policy.
Preferred standard model: symmetric IRB + shared L3VNI — many CUDNs join one fabric VRF; inter-CUDN traffic goes via L3VNI to fabric gateways (RFE-2), not per-VLAN leak. Lab only proved the one-CUDN / one-VRF case.

Hurdles — OVN CUDN and Type-5

H7–H10, H12–H13 — product limits for fabric scale

  • H7 OVN ipVRF VNI uniqueness — cannot share L3VNI 10000 across CUDNs
  • H8 Shared RT ≠ shared L3 VNI — RIB imports; VXLAN demux fails
  • H9 1:1 macVRF ↔ ipVRF — cannot attach green to blue’s router
  • H10 OVN owns Primary GW .1 — blocks fabric anycast / defaultGatewayIPs
  • H12 One fabric VRF ↔ one L3VNI — multi-RT import ≠ multi-VNI demux
  • H13 Disabling CORE L3VNI does not fix multi-CUDN; breaks symmetric IRB

Scale mismatch

Extra leaf tier vs standard many-VLAN / few-VRF leaf

CUDN leaf today

Same-subnet L2 stretches but is a dead end (OVN GW, no external routes, IPAM mandatory). One CUDN can join one fabric VRF with ipVRF. Cannot map many CUDNs into few VRFs or use fabric anycast GW.

Standard fabric leaf

~100s of VLANs into ~10 VRFs. Symmetric IRB anycast. External VTEPs and OpenShift share the same VRFs.

OpenShift must peer as a normal EVPN leaf into existing VRFs — not invent a one-CUDN-per-VRF tax on the fabric.

RFE-1 — Multi-L2 shared IP-VRF

Break 1:1 macVRF ↔ ipVRF P1

Ask: Many Primary Layer2 EVPN CUDNs attach to one shared IP-VRF so intervlan works inside the cluster VRF.

Why not fabric-only: One CUDN → one switch VRF + leak into CORE needs ~100s of VRFs (target is ~10). Multi-RT import ≠ demux (H8/H12); leak-NH limits (H11). Fabric SVIs also unreachable (RFE-3 / H10).

Hurdles: H7, H9, H12 — plus H10/H11 via blocked externalization

Accept: ≥2 Primary L2 CUDNs on different subnets share one IP-VRF with working pod intervlan; documented path toward ≥50 L2 → ≤5 IP-VRFs.

Without shared IP-VRF in OVN, and without ~100 fabric VRFs or fabric SVI handoff, CUDNs can never route to each other.

RFE-2 — Fabric L3VNI membership

Symmetric IRB + shared L3VNI — inter-CUDN on the fabric P1

Desired model: Many CUDN VLANs membership-map into one fabric VRF / one shared L3VNI. Off-subnet and inter-CUDN traffic go via that L3VNI to fabric gateways (CRB). Inter-VRF policy stays on the fabric’s several VRFs — not OVN-local routing between CUDNs, and not ~100s of VRFs + leak.

Ask: Map cluster IP-VRF to fabric L3VNI + RT so Type-5 and symmetric IRB return demux work for multiple CUDNs.

Why not fabric-only today: Dual VNI 10000 rejected (H7). Unique OVN VNIs + shared RT → return on fabric L3VNI blackholes (H8). Leak workaround abandons standard symmetric IRB scale.

Accept: ≥2 CUDNs in one fabric VRF; inter-CUDN via fabric gateways; round-trip on shared L3VNI.

Symmetric IRB shared L3VNI is how standard fabrics route between VLANs — CUDN must join that model, not invent per-VLAN VRF leaking.

RFE-3 — Primary fabric gateway

Fabric anycast or bridge-only Primary mode P1

Ask: Primary EVPN CUDNs use fabric anycast IRB as GW, or explicit bridge-only L2 — OVN must not silently own .1. Complementary to RFE-2: both put inter-CUDN L3 on the fabric (L2 hairpin to anycast vs L3VNI membership).

Why not fabric-only: CRB SVIs already exist in Vrf_CORE and work for external hosts. Pods ARP OVN 0a:58:…, never the fabric leaf. More fabric VRFs / leaks do not help if packets never leave the node — and still fail the ~10-VRF scale goal (RFE-1).

Hurdles: H10 — defaultGatewayIPs failed

Accept: Pod ARPs fabric GW MAC; off-subnet via CRB works in chosen mode; field semantics match dataplane.

Cannot use fabric SVIs + cannot stand up ~100 VRFs with leak ⇒ CUDNs never route to each other via CRB.

RFE-4 — FRR inbound BGP

Accept peers on TCP 179 (or first-class RR) P3

Ask: FRR-k8s accepts inbound BGP on :179, or a supported RR / Service DNAT story — plus selective FRRConfiguration binding.

Hurdles: H1, H2, H16 — listen 50179; ROSA dynamic IPs; {} selector matches all.

Accept: Fabric leaf/RR can initiate to cluster on 179; documented dynamic-IP pattern without per-node peer churn.

RFE-5 — Multi-cluster IPAM

Shared EVPN segments without manual reserves P2

Ask: First-class multi-cluster IPAM for shared L2 EVPN segments beyond hand-maintained complementary reservedSubnets.

Hurdles: H4, H15

Accept: Two (then three) clusters share a /24 without editing peer reserves on every change; clear errors for bad CIDRs.
